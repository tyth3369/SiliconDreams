## Runtime image layer follow-up

- The rc.5 registry layer trace showed a 437.82MB compressed dependency layer and a 1,713,377,249-byte unpacked image. The Dockerfile installed dependencies without a cache mount, leaving uv's download cache eligible for inclusion in that layer.
- Moved both `uv sync` steps onto a shared BuildKit cache mount and set `UV_LINK_MODE=copy`, ensuring runtime files remain self-contained while the package-download cache is excluded from the final image.
- Added a Dockerfile policy regression test. The exact size impact remains delegated to the real Linux container gate because Docker is unavailable on the development Mac.
- Main CI run `34815780078` passed with `torch 2.14.0+cpu`; the resulting image was `1,710,050,147` bytes. The cache mount is correct but only marginally changes total size, confirming that the remaining footprint is the installed CPU ML stack rather than uv's package-download cache. No additional release candidate was created for this non-material size change.

## GitHub-hosted deployment verification

- Added a credential-free `workflow_dispatch` action for public deployment acceptance. It accepts canonical/alias URLs, expected version and ECS public IP, then runs the existing standard-library verifier from a GitHub-hosted public network.
- The workflow has only `contents: read`, references no secrets and avoids installing the full ML dependency stack. This gives the owner a UI-driven verification path and avoids local proxy Fake-IP ambiguity.
